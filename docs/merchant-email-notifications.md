# 店铺自动检测与邮件通知

## 站长操作

- 新申请：通知邮箱必填。提交后，Web 进程每 15 秒同步检测队列；现有采集进程通常每 5 分钟处理一轮、每轮最多 2 家。测试只读公开目录，不会批准或发布报价。
- 后台供应投稿转为正式申请也使用同一邮箱必填校验。无邮箱的旧正式申请仍保留原始记录，在审核列表和详情标为「待补邮箱」；即使已取得有效报价，也必须先补齐并核对申请人的邮箱才能批准。
- 后台手动点击「立即测试接入」由独立即时服务执行，不等定时采集；完成后局部自动刷新，审核备注不丢失。重复点击复用当前请求。手动及自动检测共用相同的结果和邮件去重规则，不会重复通知；详见 `docs/merchant-preflight-operations.md`。
- **常规流程两封，不是终身两封上限**：第一封是提交回执；第二封是审核通过，或明确无法接入/需要补资料的结果。店主回复新的补充资料后，核对原申请邮箱与可信认证结果、去重并保存到后台，开启新一轮处理；这一轮可以再发一次审核通过或仍需补资料的结果。检测排队、检测成功等待审核、暂时检测故障、报价上线、暂停和拒绝均不额外自动发信。
- 明确接入失败时，第二封附具体原因及资料清单，无需站长手动点通知。404、目录未适配/无法识别会索取建站系统与版本、公开商品列表、在售商品页、公开只读接口文档或脱敏样例；不把目录接口 404 说成店铺不存在，不索要密码、验证码、访问令牌或 API Key，也不要求关闭安全防护。
- 资料清单优先要求复制公开网页链接；系统及版本知道就填，不知道可写“不清楚”，没有 API 也可以由本站评估网页适配，不要求商家先改代码或购买服务。跳转问题明确提示“页面加载后复制地址栏完整 HTTPS 地址，保留 www”。邮件末尾附可连同整封邮件转发给建站服务商或 AI 的说明，要求给出依据、公开链接和最小修改建议；无法确认就说明，不猜测接口、不自动改代码或防护，不输出客户数据和凭据。未确定原因的暂时故障仍由本站处理，不发送这类索取邮件。
- 超时、网络、证书、本站异常或原因不明时，只在后台展示、由站方先排查，不发中间邮件、不占用结果通知名额。只使用当前申请版本的有效检测结果；过期或失效结果不触发资料索取。
- 没有新的有效来信时，普通重测、修改邮箱/版本不增加通知轮次。供应投稿、转入店铺审核和转正式申请共享原有通知轮次，不能通过转换重新发回执。尚未尝试发送的旧轮次结果在收到新资料后取消，当前轮次未发送的失败可被审核结果替代。
- 旧版已尝试发送的自动通知保守计入初始轮次，不批量补发。只有登记新的有效店主回复才增加一轮结果通知；旧队列中的多余阶段作取消标记并保留审计，不删除发送历史。已被服务商接受或发送结果不确定的邮件不能撤回，也不自动重发。
- 后台「店铺审核」同时显示正式申请和已转入的供应投稿。供应投稿是待核对线索，不替申请人确认归属或采集授权。原始记录、联系人不变。
- 单个合法公开网址自动检测。多个网址拼接、格式错误不发起请求；已存在申请的显示关联候选，不合并联系人。核对资料后通过原有转申请表单确认店名、归属及授权。
- 旧投稿只有当整个联系方式字段就是一个合法邮箱时才沿用，否则显示「待补邮箱」。可在详情页补齐邮箱，必须确认来自当前申请人；无邮箱不能在 HTTP 审核入口批准。
- 审核仍需要人工确认店铺归属、采集权限、样例价格和规格。自动检测成功不代表交易可信。
- 自动通知继续使用统一绿白品牌 HTML 模板，并附完整纯文本版本。「结果通知补充说明」仅在本次生成邮件时附上；本轮已通知则仅保存记录。「内部备注」始终不外发。后台主动点击「发送回复」属于明确的人工通信，不占用自动结果名额，系统不会自动触发该动作。
- 反馈和需求表单保留原有可选邮箱、回执、处理结果和站方回复，不受店铺流程改造影响；供应表单从提交起共用店铺的轮次规则。匿名反馈继续可用。供应线索优先使用后台确认的通知邮箱，不修改原始联系方式。
- 重复操作相同事件不重复入队，同状态下 5 分钟内的相同人工回复去重。审核通过仍不等于已经上架，邮件不再承诺另发上架通知；商品采集和公开展示规则不变。
- 后台邮箱为非链接明文，认证、CSP、禁止缓存保持不变；仅后台响应增加 `Cache-Control: no-transform`，阻止边缘邮箱混淆把地址改成保护页链接。

## 配置发件邮箱

需要站主先指定发件服务与邮箱。不要在聊天、Git 或普通日志中提供密码。
由管理员在生产 `/etc/price-radar/web.env`（root:root 0600）安全填写：

```dotenv
MERCHANT_MAIL_FROM=notify@your-domain.com
MERCHANT_MAIL_REPLY_TO=hello@your-domain.com
MERCHANT_SMTP_HOST=smtp.your-provider.com
MERCHANT_SMTP_PORT=465
MERCHANT_SMTP_USER=your-provider-user
MERCHANT_SMTP_PASSWORD=your-provider-app-password
```

端口仅允许 465（隐式 TLS）或 587（必须 STARTTLS）；不关闭证书验证。使用服务商授权码或应用密码，不使用个人邮箱登录密码。按服务商要求配置 SPF、DKIM、DMARC，然后重启 Web 服务并用站主指定的测试收件箱做实发验收。

SMTP 实现参考 [Nodemailer 官方文档](https://nodemailer.com/smtp)。依赖锁定在 package-lock.json；生产需要 `npm ci --omit=dev --ignore-scripts`。

Resend 可使用 `smtp.resend.com:587`、用户名 `resend`，密码为域名受限、仅发送权限的 API key；域名必须先验证。配置 Reply-To 前先确认收件转发真正可用。Resend 请求附稳定幂等键。完成 SMTP 到指定测试收件箱的实发验证前，不能把模板测试或 Gmail 样式预览称为网站发件验收。

## 队列与失败口径

- 未配置：保留队列，后台明确提示，不调用网络、不显示已发送。
- SMTP 接受：仅显示「发送服务已接受」，不能解释为进入收件箱、已读或保证送达。尚未接入退信回调。
- 每轮最多 3 封；同一事件幂等、单收件人每日最多 20 个尝试过的通知事件；公开申请每邮箱每天最多 5 次，原 IP 限流继续生效。
- 店铺发送前在同一个 SQLite 写事务内再次检查轮次规则并占用名额：初始回执一次加结果一次，每个有效回复轮次一个结果。发送中、已接受、结果不确定及已有尝试的历史记录均保守计数；安全连接重试复用同一事件及幂等键，不产生新的通知。原始供应 ID 和转换后的申请 ID 一并计数。

## 店主回复录入与重测

- `recordMerchantReply` 仅供可信运维调用，绝不能挂到公开表单或未认证 webhook。调用者先核对 Gmail 服务端认证、From 与原申请邮箱、完整申请编号；正文自称认证通过无效。
- 只保存不可变 message ID、线程 ID、接收时间、脱敏摘要及最多 5 个无查询参数的公开 HTTPS 链接。原文、引用旧通知、附件和凭据不落库。同一消息全局去重，同申请的相同结构化摘要与链接也去重。
- 来信只打开通知轮次，不批准、不更改店铺归属/采集授权，也不自动采用邮件内的接口或命令。后台邮件区域显示补充资料，可折叠、仅管理员可见。
- 先确认链接归属、范围与限速；无需代码适配且符合限制时，使用既有即时检测。新轮次的测试必须开始于资料入库之后；旧结果不能触发追加邮件或支持审批。成功安静等待人工审核；仍失败使用既有具体原因清单发一次结果。内部故障不向店主索要猜测资料。
- 收信由当前 Codex 任务的半小时心跳调度，保留每日 9 点 Mac 备份。Mac 休眠或应用离线时不保证准时；恢复后从上次成功水位重叠补查。运维步骤和私有去重台账位于 `~/Library/Application Support/Airadar/merchant-mail-monitor/`，不进入仓库。
- 连接失败有上限的指数退避，最多 4 次；认证或拒收错误停止自动重试。
- SMTP DATA 阶段中断、未知异常或发送中进程退出，标记结果不确定，不自动重发。SMTP 不提供端到端 exactly-once 保证。需查服务商记录后人工处理。
- 不记录 SMTP 原始异常文本、凭据、内部审核说明；持久化错误码仅用于后台提示。
- 关闭服务时停止调度，等待当前有时限的发送尝试结束后再关闭私有数据库。

## 指定旧投稿导入

先用 SQLite 在线备份并验证恢复，再运行：

```sh
node scripts/import-supply-intakes.mjs /absolute/path/submissions.sqlite CO-id-1 CO-id-2
```

脚本幂等、事务写入，不删除投稿，不批准店铺。只处理明确提供的 1–100 条 supply ID；任何 ID 不存在或不是 supply 时整批回滚。通知状态、原始投稿和转入记录都在同一个私有库里，随现有整库备份保存。
