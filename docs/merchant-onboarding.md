# 店铺申请与审核

店主须先注册登录、验证邮箱并补齐手机号及微信/TG/QQ 中一项联系方式，才能在 `/submit-shop` 提交公开店铺地址、主营品类，并授权联系核验与公开目录采集。手机号仅做格式检查，未短信验证。申请联系资料取当前账号，服务端也拒绝游客提交。详见 [商家注册与联系资料](merchant-account-registration.md)。首次申请由站长在 `/admin/merchants` 人工核验店铺归属和采集权限；批准时必须分别确认两项，并填写可追溯的审核说明。联系方式和审核材料仅保存在私有申请数据库，不在公开页面展示。

批准后进入定时采集流程。适配器支持且采集成功后才展示有效报价；独立站等暂不支持的平台显示“待适配”，需要人工补充支持。审核通过不等于已经接入。公开页面仅显示中性的“店铺已收录”标识，表示店铺信息已收录，不代表商家信用、商品质量或交易安全保证，也不代表 API 直报或 Sponsor 广告背书。内部核验记录、审核门槛与通知流程保持不变。

暂停会撤下收录标识，并在下一采集周期移除动态采集目标；仅通过该动态接入产生的报价在该周期撤回。若店铺原本就在既有公开直采目录，其独立公开报价仍可保留。重新批准也需要核验确认和审核说明。

## 已有供应投稿转为店铺申请

后台 `/admin?kind=supply` → 打开供应投稿 → **转为店铺申请**。

1. 页面带入原投稿的网址、联系方式、主营品类和说明。投稿标题不等于店名，需核实并填写实际店铺名称；网址应为公开的 HTTPS 店铺主页。
2. 另行确认投稿人有权代表店铺，并取得公开商品目录采集、展示许可。原供应投稿的内容确认不等于此项授权，两项确认框默认不勾选。
3. 填写授权核验依据，然后点击 **创建待审核申请**。只创建待审核记录，不自动测试、批准、联网或发布报价。
4. 在店铺申请详情继续原有接入测试与人工审核流程。详情可回到原投稿并查看转换时间和核验说明；转换操作者同时记录在私有审计表中。

原投稿内容和处理状态不会被覆盖。重复提交同一投稿返回原关联申请；其他投稿若对应已存在的店铺，仅提示查看现有申请，不自动合并联系人。采购、反馈不能通过此入口转换。上线不会自动搬迁历史投稿。

转换关联及审计分别保存在私有数据库的 `merchant_submission_links`、`merchant_conversion_actions`，与新申请在同一事务中写入；它们不进入公开店主标识或采集清单。现有整个私有 SQLite 数据库备份会包含这些新增表。

## 部署与运行数据

`MERCHANT_BRIDGE_DIR=/opt/linc/apps/price-radar/merchant-bridge` 同时写入应用 `.env`（采集服务）和 `/etc/price-radar/web.env`（网页服务）。部署脚本保留已有环境变量和凭据；若该配置已指向其他目录，部署失败并要求运维核对，避免意外扩大读写范围。不要打印环境文件。

桥接目录归 `deploy:deploy`，权限 `700`，其中清单应为 `600`。网页服务只额外获得该目录写权限，行情 `data` 仍只读；采集服务可读取桥接清单，但仍无法访问 `submissions`、`analytics` 和网页凭据文件。清单只能包含采集必要的公开店铺信息，不能包含联系方式和审核材料。

代码同步、代码备份及回滚均排除 `merchant-bridge`，运行中的清单不会被代码回滚覆盖。申请记录和审核日志随私有 `submissions` 数据库备份；恢复申请数据库后，网页服务启动时可重建桥接清单。桥接目录不是申请记录的备份源。
